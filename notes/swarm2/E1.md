# E1: GPU XGBoost in a new C: env (cs2gpu)

Date: 2026-10-13. Host: Windows 11, AMD Ryzen 7 7840U (8C/16T), RTX 3080 20 GB, driver 591.86 (CUDA 13.1).
Scope: new pixi project on C: only. G: project env (`G:\pureskill\csds-cs2\.pixi`) not modified. Nothing under E:.

## Result in one line

conda-forge has a win-64 CUDA build of xgboost 3.4.2 (`cuda129`). A plain `pixi add xgboost` picks the CPU build,
so the CUDA build has to be pinned. With the pin, `xgboost.build_info()["USE_CUDA"]` is True and `device="cuda"` trains.
On the synthetic benchmark CUDA is about 87x faster than CPU with default threads, but CUDA and CPU models are not
numerically equivalent (see E1-2).

## Commands that worked (in order)

```
"C:\Users\13144\.pixi\bin\pixi.exe" init "C:\Users\13144\envs\cs2gpu" --channel conda-forge --platform win-64
"C:\Users\13144\.pixi\bin\pixi.exe" add --manifest-path "C:\Users\13144\envs\cs2gpu\pixi.toml" --platform win-64 "python=3.12" xgboost polars pyarrow numpy scikit-learn pandas
# first solve -> libxgboost-3.4.2-cpu_hd161407_0 (CPU build). Not sufficient.
# manual edit of pixi.toml: add
#   [system-requirements]
#   cuda = "12.9"
# without it pixi does not expose __cuda to the solver and the cuda pin below fails with "__cuda ... no candidates".
"C:\Users\13144\.pixi\bin\pixi.exe" add --manifest-path "C:\Users\13144\envs\cs2gpu\pixi.toml" --platform win-64 "xgboost=3.4.2=cuda129*" "libxgboost=3.4.2=cuda129*"
# -> libxgboost-3.4.2-cuda129_h8216274_0 (win-64). Works.
```

The resulting manifest has `xgboost = { version = "==3.4.2", build = "cuda129*" }` and the same for `libxgboost`.
pixi 0.79 warns that `[system-requirements]` is deprecated in favor of virtual packages on `platforms`
(`platforms = [{ name = ..., platform = "win-64", cuda = "12.9" }]`). That form was not tested.

No PyPI search was needed: the conda-forge win-64 build already has CUDA.

## Benchmark (synthetic; all workload parameters are ASSUMPTIONS)

Workload: 1,000,000 train rows and 100,000 holdout rows, 50 float32 N(0,1) features, binary:logistic target with a
nonlinear logit plus noise, seed 12345. hist, max_depth 4, eta 0.1 (ASSUMPTION), 200 trees, 5-round untimed warm-up.
Host was at 100% CPU and the GPU at 13.7 GB / 100% util from other processes at start (contention; see E1-3).

| config | timed runs (s) | median (s) | s/tree | holdout logloss |
|---|---|---|---|---|
| cpu, default threads (16) | 399.585 (1 run) | 399.585 | 1.998 | 0.590320 |
| cpu, nthread=1 | 80.057, 81.517 | 80.787 | 0.404 | 0.590320 |
| cuda (device=cuda) | 6.302, 4.122, 4.590 | 4.590 | 0.023 | 0.595471 |

- Speedup CUDA vs CPU default: 87.1x. CUDA vs CPU 1-thread: 17.6x.
- CPU default-thread and 1-thread models are identical (same logloss, same prediction diffs), so thread count does not change CPU results.
- CUDA vs CPU holdout predictions: max abs diff 0.2006, mean abs diff 0.0192.
- Peak working set in the benchmark process: about 1.1 GB.

## Findings

### E1-1 (high): CUDA xgboost works in a new C: env, but only with an explicit build pin
- supported. `build_info()["USE_CUDA"]` is True; `device="cuda"` trains in `E1_check_build.log` and `E1_bench.log`
  (`config_device` = "cuda:0").
- An unpinned solve picks the CPU build (`libxgboost-3.4.2-cpu_hd161407_0`) even with `__cuda` 13.1 on the host, because
  pixi does not expose `__cuda` unless `[system-requirements] cuda` is set. The CUDA pin also needs that setting.
- The G: project env is on the CPU build (its conda-meta lists `libxgboost-3.4.2-cpu_hd161407_0`, read-only check), which
  explains why it has no CUDA. Fixing G: means a re-solve with the same pins. Not done here (G: env is out of scope).

### E1-2 (high): CUDA and CPU predictions differ materially; switching the training device changes the model
- supported. At 1M rows, holdout logloss 0.595471 (cuda) vs 0.590320 (cpu). CUDA is about 0.0052 worse.
  Mean abs prob diff 0.0192, max 0.2006.
- At 100k rows the mean abs diff is 0.0186 and the logloss gap is +0.00026, so the gap is not only a size effect; it is
  a per-prediction difference with a tiny loss difference.
- Cause not verified (plausible: different quantile/histogram cut construction between the CPU and CUDA hist paths).
- Consequence for the plan: a G: baseline on CPU (test logloss 0.43660) is not directly comparable to a CUDA run. Pick one device
  per comparison and re-baseline before any cross-device claim. Note: this was measured on synthetic data with one seed
  (ASSUMPTION about generality); it has not been checked on the real CS2 features.

### E1-3 (medium): timings measured under 100% host CPU and high GPU load from other processes
- supported with caveat. Median CUDA 4.59 s (0.023 s/tree) for 200 trees at 1M x 50; CPU 1-thread 80.8 s; CPU default 399.6 s.
- The load was from other python processes (two with about 4,900 CPU-seconds each) and the GPU was at 100% util on start.
  Treat speedups (87x, 17.6x) as contended figures. Rerun on an idle host before quoting them as capability numbers.
- The CPU default-threads figure is one run only (too slow to repeat under this load).

### E1-4 (medium): CPU multi-threading collapses under this load (OpenMP oversubscription suspected)
- supported (behavior), cause suspected. At 100k rows, 10 trees: 1 thread 0.050 s/tree; 2 threads 1.43 s/tree;
  4 threads 1.76; 8 threads 5.07; 16 threads 1.16 with runs of 22.5 s and 0.74 s.
- Interpretation: OpenMP threads wait on each other when the host is saturated. Not proven; would need an idle-host rerun.
- Operational consequence: on this machine, while the swarm runs, set `nthread` explicitly and keep CPU jobs small.
  Default threads (16) gave the worst CPU time.

### E1-5 (medium): memory/commit pressure caused a CPU "bad allocation" and native crashes
- supported (correlation), cause inferred. The first full benchmark attempt failed at the first CPU timed run with
  `XGBoostError: bad allocation` after the warm-up (log overwritten by the rerun).
- Later, the E1_parity run's python process died with exit code -1073740022 (0xC000070A) during the 1M step. The Windows
  Application log shows repeated `python.exe` APPCRASH events with exception 0xc000070a, faulting module ntdll.dll,
  fault offset 0xC87A4 (same each time), faulting path = this env's python.exe, at 17:06:16, 17:06:56, 17:07:34, 17:07:38.
- At the time, system commit charge was 70.7 GB of an 81.2 GB limit and free RAM about 6.3-7.5 GB. Other processes hold
  most of it. One benchmark process was ~1.1 GB, so the cause is system-wide commit pressure, not this job alone (inferred).
- The 1M parity point is not rerun. The 1M CPU-vs-CUDA numbers come from `E1_bench.py`, which completed; both CPU configs
  gave the same predictions there.
- Operational consequence: keep per-job memory low, avoid starting several large GPU/CPU jobs at once.

### E1-6 (low): install size and exact commands
- supported. Env prefix about 2.15 GB installed; rattler cache 6.23 GB (shared); exact commands in "Commands that worked".

### E1-7 (low): env location and manifest warning
- supported. Env is under `C:\Users\13144\.pixi\workspace-envs\cs2gpu-15282324412032665829\envs\default`, not inside the project
  folder. `[system-requirements]` produces a pixi deprecation warning (works, not blocking).

## What was not done or not verified

- No idle-host timing run. All timings are contended (E1-3, E1-4).
- No CUDA check on the real CS2 features. Parity measured on synthetic data only (E1-2).
- No G: env change, and no run with the G: interpreter (only read its conda-meta). The G: env is still CPU-only.
- PyPI xgboost CUDA wheels were not searched; not needed because conda-forge had a win-64 CUDA build.
- The cause of the CPU-vs-CUDA model difference (E1-2) was not investigated.
- The 1M parity point was not rerun after the crash; the benchmark's CPU and CUDA runs both completed.
